# 品質保証と責任範囲

本書は Menreiki の品質モデル（何を保証し、何を保証しないか）と、
役割ごとの責任範囲、品質保証プロセスを定める規範文書である
（[ADR-015](adr/015-quality-assurance-and-responsibility.jp.md)）。

## 1. 品質モデル

### 1.1 構造的に保証すること

以下はソフトウェアの構造によって成立する性質であり、自動テストで
担保する。**これらの破れは重大な不具合として最優先で修正する。**

| 保証 | 根拠となる構造 |
|---|---|
| 文書内容を外部へ送信しない | 解析・OCR・変換・監査はすべてローカル実行。LLM/VLM クライアントは localhost 以外への接続を構造的に拒否する |
| 出力に原本の隠れた情報が混入しない | 出力PDF/Markdown/画像は**変換後のページ画素のみ**から再構築する。原本のテキストレイヤー・メタデータ・注釈・添付・スクリプトは構造上引き継がれない |
| 原本を改変しない | 原本はプロジェクトフォルダへコピーされ、以後は読み取りのみ |
| 適用内容が監査可能である | 適用計画は実行前に `decisions/plan.json` として保存され、監査は出力を再OCRして変換対象の残存を照合する |

### 1.2 ベストエフォートであること（保証しないこと）

以下は**候補の提案・補助**であり、網羅性・正確性を保証しない。

- **検出の網羅性** — 検出器は意図的に過検出気味に設計しているが、
  見落とし（偽陰性）は必ず存在しうる。手書き・低解像度・特殊レイアウト・
  画像内文字・未知の表記は特に漏れやすい。
- **OCRの正確性** — Windows OCR の読み取りに依存する。誤読・文字欠落は
  発生しうる（例: 長い社名の一文字欠け）。
- **AI提案（LLM/VLM）** — ローカルモデルの出力は参考情報であり、
  誤り・見落とし・位置未特定を含みうる。レビュアーが採用しない限り
  何も適用されない。
- **法令適合性** — 特定の法令・規制（個人情報保護法、GDPR等）への
  適合を保証しない。要件への適合判断は利用者が行う。

### 1.3 人間の最終責任

**出力を公開・共有してよいかの最終判断は、常にレビュアーが負う。**
監査の Pass は「設定された検査を通過した」ことを意味し、絶対的な
安全を証明しない。公開前の目視確認を省略してはならない。

## 2. 役割別の責任範囲

| 役割 | 責任 |
|---|---|
| **開発（本プロジェクト）** | §1.1 の構造的保証の維持。不具合の修正と再現テストの追加。既知の限界の文書化（ヘルプ・README）。OSSとしての提供は MIT/Apache-2.0 に基づく無保証である |
| **提供者**（本ツールを組織内・第三者へ配布/運用する者） | 利用者への §1.2/1.3 の周知。運用環境の管理（OSのOCR言語パック、ローカルLLMの構成、SSHトンネル）。プロジェクトフォルダの保管・アクセス制御・廃棄ポリシーの策定 |
| **レビュアー**（利用者） | 候補の判断と最終目視確認。監査の実行と残存への対処。**プロジェクトフォルダの保護**（後述）。出力の公開可否の最終判断 |

### プロジェクトフォルダは機密である

`*.menreiki` フォルダには**原本のコピー・全ページ画像・OCR全文**が
含まれる。出力PDFが安全でも、プロジェクトフォルダが漏れれば原本が
漏れる。保管場所のアクセス制御と、不要になった時点での確実な削除は
利用側の責任である。

## 3. 品質保証プロセス

- **TDD** — 全ての不具合修正は、その不具合を再現するテスト
  （ユニット／統合／E2E のいずれか）を伴う。検出の見落とし・誤検出は
  `test-documents/typst/` にユースケース別フィクスチャとして再現を
  固定する。
- **テスト階層**
  1. ユニット（クレート単位: 検出規則・OCR行結合・編集計画・描画）
  2. 統合（プロジェクトパイプライン: 実 pdfium・実 Windows OCR）
  3. フィクスチャ検証（架空名のみのユースケース別文書。実在の名称を
     フィクスチャに含めてはならない）
  4. E2E（Playwright による実アプリ操作: 検索→判断→適用→出力→監査Pass、
     およびUI回帰）
- **リリース判定基準** — `cargo test --workspace` と E2E スイートの
  全緑を必須とする。
- **既知の限界の反映** — §1.2 に類する新たな限界が判明したら、
  アプリ内ヘルプおよび README に反映する。
- **脆弱性・漏洩経路の扱い** — 「§1.1 構造的保証の破れ」に該当する
  報告は severity 最高として扱う。
